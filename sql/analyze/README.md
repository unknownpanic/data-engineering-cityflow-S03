# Лабораторна №3 · CityFlow

**Основний документ:** `Laboratorna_3_CityFlow_v4.docx`.

## Що потрібно

Власна PostgreSQL 16+ і завершена ЛР №2 з таблицями `core`. Використовуйте той самий SQL-клієнт (наприклад, DBeaver, pgAdmin або psql) і те саме підключення. Не створюйте іншу базу чи іншу модель для цієї роботи.

Нові набори даних, Python, API, Docker і встановлення додаткових бібліотек не потрібні. Дані різних студентів не змішуйте. Джерело — **ваші прийняті таблиці**, а не всі рядки брудних CSV.

Скопіюйте `sql/lab03/` та `docs/lab03/` у свій наявний репозиторій, у гілку `lab/03-sql-analysis`. Попередню версію SQL зафіксуйте окремим комітом перед заміною. Не запускайте старий `00_setup_demo.sql` разом із цим комплектом.

## Межі даних

- `core.*` — незмінний результат ЛР №2; тут ми лише читаємо дані.
- `lab03_cf.settings` — зафіксований період аналізу.
- `lab03_cf.v_period_orders` — готовий SELECT усіх замовлень цього місяця.
- `lab03_cf.v_daily_orders`, `v_running_orders`, `v_latest_customer_order` — ваші три представлення.
- `lab03_cf.bench_*` — окремі копії/параметри тільки для експерименту з індексом.
- Старі `lab03` та лекційна `lecture03` не використовуються й не видаляються.

`00_prepare.sql` під час першого запуску обирає перший календарний місяць із `delivered`. На повторному запуску період не змінюється. Якщо після цього перезавантажили `core`, завершіть звірку ЛР №2 і свідомо перевірте обраний період; не порівнюйте результати з двох різних snapshot.

| Крок | Файл | Що зробити |
|---|---|---|
| 1 | `00_prepare.sql` | Виконати повністю. Записати параметри й кількості. |
| 2 | `01_daily_report.sql` | Виконати діагностику, дописати свій `v_daily_orders`. |
| 3 | `02_check_daily.sql` | Виконати; очікується PASS, нуль різниць за валютами. |
| 4 | `03_windows.sql` | Дописати `v_running_orders` та `v_latest_customer_order`. |
| 5 | `04_check_windows.sql` | Виконати; обидва результати PASS, кількості збігаються. |
| 6 | `05_bench_prepare.sql` | Виконати один раз перед експериментом. Записати розмір копії й фільтри. |
| 7 | `06_bench_query.sql` | Без індексу: 1 прогрів + 3 вимірювання. |
| 8 | `07_bench_index.sql` | Створити один індекс та оновити статистику. |
| 9 | `06_bench_query.sql` | З індексом: 1 прогрів + 3 вимірювання того самого запиту. |
| 10 | `08_bench_check.sql` | Очікується PASS і `difference_rows = 0`. |

Файли 01 і 03 — заготовки, а не готові розв’язки. Дописується лише SQL із завдання. Файли перевірок змінювати для отримання PASS не можна. Якщо представлення ще не створене, відповідна перевірка завершиться повідомленням «relation does not exist» — спершу виконайте потрібний крок, а не пропускайте перевірку.

**Не запускайте 05 повторно між вимірами:** він перестворює власні таблиці `bench_*` без індексу. Після 07 останній запит до `pg_indexes` має показати створений індекс. Навіть якщо план залишився `Seq Scan`, запишіть фактичні результати.

## Запуск SQL

Найпростіше: відкрийте потрібний файл у SQL-клієнті, переконайтеся, що обрано вашу базу ЛР №2, і виконайте **весь файл**. Якщо клієнт показує лише останню вибірку, для звіту запускайте діагностичні SELECT окремо або відкрийте всі результати виконання.

Альтернатива через psql (підставте власні користувача та назву БД):

```bash
psql -h localhost -U <ваш_користувач> -d <ваша_навчальна_БД> \
  -v ON_ERROR_STOP=1 -f sql/lab03/00_prepare.sql
```

Пароль вводьте через запит клієнта, не зберігайте його в SQL чи Git. Для вимірювань беріть **Execution Time** з плану, а не час відображення таблиці у клієнті. Не очищайте системний кеш і не міняйте серверні налаштування планувальника.

## Що здати

Три власні VIEW у двох SQL-файлах, звіт за шаблоном, результати перевірок, текст планів `plan_before.txt` і `plan_after.txt`, вимірювання та AI BLACK BOX. Після перевірки — PR і тег `lab-03-v1`. Повні CSV та дампи не потрібні у Git.

## Важливі уточнення щодо плану курсу

Ця редакція використовує **реальні таблиці CityFlow з ЛР №2 на всіх обов’язкових етапах**, а не окремі демо-таблиці з кав’ярнями. Числа з архіву S01 в документі — лише пояснювальний фрагмент; у звіті мають бути ваші результати.

У погодженому ширшому плані є вибір останнього стану з історії подій. Проте обов’язкові таблиці ЛР №2 ще не містять такої історії. Тому тут та сама техніка `ROW_NUMBER` застосовується до **останнього створеного замовлення клієнта за місяць**, із його поточним статусом. Історію зміни статусів не відновлюємо з одного snapshot і не генеруємо додатково.
